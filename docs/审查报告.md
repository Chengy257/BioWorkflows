# RNA-seq 工作流全面审查报告

> 审查日期：2026-09-03
> 审查范围：`rna-seq-workflow/` 全部 35 个文件（4 个流程入口、6 个规则文件、18 个脚本、3 个配置、样例数据）
> 审查方式：逐文件人工通读 + 与示例数据（sample_info.csv）交叉验证
> 结论速览：**上游比对定量主线设计合理，但存在 8 个阻断性问题（P0）**——当前状态下流程无法在新环境开箱运行，且统计汇总环节对仓库自带的示例样本数据即会产生错误结果。

## 3. P0 — 阻断性问题

### P0-1 硬编码绝对路径遍布全流程，且混用两套根路径
- **位置**：
  - `rna-seq-workflow/main_runRNA-seq.sh:5-6,11-12`（config/smk 指向 `/home/chengyu/...`）
  - 全部 4 个入口 `*.smk:2-3`：`configfile:`/`include:` 均为 `/home/chengyu/workflows/snakemake/rna-seq-workflow/...` 绝对路径
  - `rules/RNA-seq_upstream.smk:179`（`/share/workflows/rna-seq/scripts/run-featurecounts.R`）、`:193`（`/home/chengyu/.../featureCount.R_result_merge.sh`）
  - `rules/RNA-seq_downstream.smk:63,77,89`（`/usr/bin/Rscript` + `/share/workflows/...`）
  - `rules/RNA-seq_upstream_AS.smk:201`、`rules/RNA-seq_lncRNA_DenovoIdenti.smk:43,65,75,104,133,157,212`
- **影响**：换机器、换用户、换部署目录必然失败；同一仓库内 `/home/chengyu/workflows/...` 与 `/share/workflows/...` 两套根并存，无法整体迁移。
- **建议**：所有 `include:`/`configfile:`/脚本调用改为相对工作流根目录（Snakemake 的 `workflow.basedir` 或直接相对路径）；外部脚本一律随仓库走。

### P0-2 conda 环境定义文件缺失，`--use-conda` 必然失败
- **位置**：规则中大量 `conda: "rna-seq"` / `conda: "common"` / `conda: "lncrna"`（如 `RNA-seq_upstream.smk:14,34,49` 等），但仓库中不存在任何 `envs/*.yaml`。
- **影响**：主控脚本 `main_runRNA-seq.sh:19` 带 `--use-conda` 运行时，Snakemake 找不到环境文件直接报错。
- **建议**：新建 `envs/` 目录，为各步骤编写并固定版本的 conda 环境文件（见优化路线图 1.2）。

### P0-3 依赖的外部脚本不在仓库中，count 矩阵无法生成（DEG 主线断裂）
- **位置**：`scripts/featureCount.R_result_merge.sh:16-17,24` 调用 `/home/chengyu/myscripts/njoin.sh` 与 `transposition.sh`。
- **影响**：`4.expression/count.matrix.tsv` 无法产出，DESeq2 差异分析整条链路中断；且该脚本第 17 行将同一拼接结果写两遍（`all.feacount` 与 `all.log` 内容相同），逻辑可疑。
- **建议**：用仓库内一个自包含脚本（建议 Python/pandas）重写多样本 count/FPKM/TPM 合并与转置，删除外部依赖。

### P0-4 lncRNA 管线终点调用空壳脚本
- **位置**：`rules/RNA-seq_lncRNA_DenovoIdenti.smk:212` 调用 `scripts/featureCount.R_result_merge.py`，该文件仅有不完整 shebang（`#!/usr/bin/`）与注释头，**无任何代码**。
- **影响**：`5.expression/lncRNA/count.matrix.tsv`、`GeneExpression_TPM.xls` 永远无法生成，lncRNA 入口（`RNA-seq_up_lncRNA.smk`）的最后一步必然失败。
- **建议**：与 P0-3 合并解决（同一份合并脚本服务两处）。

### P0-5 死/损坏脚本混在生产目录
- **位置与证据**：
  - `scripts/enrich_KEGG_clusterProfiler.R:48` 存在语法错误（`as.data.frame(ekegg@result %>% p.adjust <= 0.05))` 括号不匹配），`:55-64` 引用从未定义的 `ego_BP/ego_MF/ego_CC`；
  - `scripts/getExpr_featureCounts.sh:18` 的 `featureCounts -T $threads -a $gtf -o` 缺参数即中断，`:26` `if [ "fraction1" > 0.8 ]` 是字符串字面量比较（恒真）且文件在此截断；
  - `scripts/check_strandness.sh` 全文是 Snakemake shell 模板的拷贝，含 `{input.bed}`、`{{print $1}}` 等未替换占位符，不可执行。
- **影响**：当前主流水线未调用这三者（属"死代码"），但混在 `scripts/` 中极易被误用。
- **建议**：删除或移入 `archive/`；确需保留功能则修复后纳入流程。

### P0-6 Mapping_stat 统计表对仓库自带样本数据即出错（错位 + 截断）
- **位置**：`rules/RNA-seq_upstream.smk:117-123`；AS 版本 `rules/RNA-seq_upstream_AS.smk:133-139`。
- **两个独立缺陷**：
  1. `ls 3.align/*_Log.final.out | cut -d_ -f1` 用第一个下划线截断样本名——仓库示例 `sample_info.csv` 中样本全部含下划线（`anticeres_1`、`ctal_1_1`……），统计表 ID 必然被截成 `anticeres`、`ctal`；
  2. Trim Galore 双端模式对每对 fastq 产出**两份** `*_trimming_report.txt`，`cat ... | fgrep "Total reads processed"` 得到 2N 行，与 N 个 ID `paste` 错位（upstream 版）；AS 版本又加了 `head -1`，只取第 1 行，N-1 个样本的 Clean_Reads 全空——两个版本错法还不一致。
- **影响**：交付给用户的比对统计表内容错误。
- **建议**：改为按 `*_Log.final.out` 逐文件 awk 解析（样本名 = 去掉 `_Log.final.out` 后缀），Total/Clean reads 从同一文件体系按样本配对提取，禁止跨文件按行序对齐。

### P0-7 "control" 组名硬编码，无对照组则无结果
- **位置**：`scripts/runDESeq2_multiGroup_230705.R:42`（`grepl(control_name, ref)`，默认 `control`）；`scripts/getGroups.py:18,31`（硬编码 `!= "control"` 与 `"_vs_control_"`）。
- **影响**：脚本名为 multiGroup，实际只输出"各组 vs control"的比较；样本分组中若无名为 `control` 的组，DEG 结果与后续组间比较全部为空且**无任何报错**。
- **建议**：`control_group` 提升为配置项并做启动校验；或实现真正的全两两比较开关。

### P0-8 富集分析物种与注释资源硬编码为水稻
- **位置**：
  - `scripts/enrich.sh:43`（GSEA 物种参数固定传 `osa`，函数形参 `$2` 实际未使用）、`:49`（注释文件写死 `/home/chengyu/references/osa/rap/...`）
  - `scripts/enrich_GO_KEGG_clusterProfiler_gProfilerGO.R:11-12`（从作者家目录安装 org.Osativa.eg.db tarball）
  - `scripts/multi_enrich_GOKEGG.R:18`（KEGG ID 映射表写死 `/share/data/reference/osa/...`）
  - `scripts/DEGgroupCompare.sh:21`（ParaFly 绝对路径）、`:23`（osa 注释）
- **影响**：人类数据依赖另一份复制脚本 `enrich_GO_KEGG_..._hsa.R`（代码漂移已出现：两份文件 .libPaths 都不同）；新增物种需再复制。
- **建议**：物种配置化（`species: osa/hsa/...` → OrgDb、keyType、KEGG code、注释文件、bed 一并在 config/species 配置段解析）；ParaFly 换成 Snakemake 原生并行。

## 6. 方法学评估（值得保留的设计）

审查不仅找问题，也确认以下**符合领域最佳实践、重构时应保留**的设计：

1. **链路选型**：FastQC → Trim Galore → STAR two-pass → featureCounts → DESeq2 是 bulk RNA-seq 标准主线；原始 count 进 DESeq2、TPM/FPKM 仅作展示，用法正确。
2. **链特异性自动推断**：`infer_experiment.py` 推断 strandedness 并自动传递给 featureCounts（`-s`）与 StringTie（`--rf/--fr`），是本流程的亮点（`upstream.smk:126-145`、`upstream_AS.smk:163-185`）。
3. **差异分析参数**：padj + FC 双阈值、Down 采用 `FC <= 1/FoldChange` 对称判定、可选 `~ batch + group` 设计，均正确（`runDESeq2:54-55,9-26`）。
4. **富集分析模式**：`pvalueCutoff=1` 全量输出后按 `p.adjust<=0.05` 过滤（保留完整结果便于复查）；aPEAR 网络去冗余、compareCluster 组间比较、GSEA 使用全转录组排序谱（`decreasing=TRUE` 命名向量），方法得当。
5. **lncRNA 鉴定策略**：StringTie 组装 → merge → gffcompare 取 class code "u" → 长度 ≥200nt → CPC2/CNCI 双编码势预测 → Pfam/NR 同源过滤，是主流 de novo lncRNA 鉴定组合。

## 7. 总体结论

- **上游比对定量与下游统计方法选型正确**，链特异性处理有亮点；问题集中在**工程化**层面：路径硬编码、环境未版本化、依赖脚本缺失、汇总统计正确性、物种不可配置。
- 按 `docs/优化路线图.md` 的三阶段推进后，预期达到：**新项目仅凭 `config/` + rawdata 即可在任意 Linux 环境端到端复现**。
